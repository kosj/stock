## 변경한 동작

주 예약은 금요일 16:12 KST를 유지한다. 금요일 17:42·20:42, 토요일 09:42·15:42 KST에 보완 슬롯을 추가한다. 모든 슬롯과 수동 운영 실행은 `hybrid-ensemble-weekly`라는 **동일한 concurrency group**, `cancel-in-progress: false`를 사용한다. 별도 dispatch 권한이나 DB 테이블/마이그레이션은 추가하지 않는다.

`scripts/weekly_execution.py`는 무거운 의존성 설치 전에 stdlib만으로 다음을 검사한다.

1. GitHub가 기록한 run 생성 시각으로 대상 금요일을 계산한다. 금요일 16:12부터 토요일 18:00 KST까지만 자동 복구한다. 현재 시각도 같은 복구 창 안이어야 한다. 설치/학습 동안 자정이 넘어도 `WEEKLY_RUN_DATE`를 고정해 같은 금요일 배치에 기록한다. 이전 주의 오래된 실행을 다음 주로 바꾸어 발행하지 않는다.
2. 기존 서버 service role 인증으로 `recommendation_batches`를 **GET**한다. 완료 배치가 있으면 설치/학습 없이 건너뛴다. 학습 직전에도 다시 확인한다.
3. 해당 기본 브랜치/워크플로/주차의 Actions 기록과 실행 영수증 artifact를 페이지 끝까지 조회한다. 최근 80건만 확인하는 방식은 사용하지 않는다. 페이지 상한 초과, HTTP/JSON 오류, 권한 오류는 학습 허가로 취급하지 않는다.
4. 실행 결과를 분류한다. 완료 배치와 영수증 확인은 모든 운영 수동 실행에도 필수다. 호환 입력 `skip_if_done=0`으로 우회할 수 없다. 운영 실행은 기본 브랜치에서만 허용한다.

| 증거 | 동작 |

| 해당 날짜의 완료 배치 | `skipped / published_batch`; 학습·발행 안 함 |

| 설치 실패 또는 품질 보고서 생성 전 명시적 프로세스 실패 | 해당 주차 **최대 2회 시도(최초 + 재시도 1회)** 내에서만 재시도 |
| 품질 평가 완료 후 오류, 성공인데 결과 없음, runner 중단으로 결과 불명확 | 자동 재학습 차단; 운영자 확인 필요 |

| pending concurrency 실행이 runner 배정 없이 취소됨 | 학습한 실행으로 세지 않음 |
| dry-run 영수증 | 운영 완료/보류 증거로 사용하지 않음 |

품질 보류는 `hybrid_ensemble.py`의 **실제 품질 거절 분기**에서만 결과 파일과 전용 exit 78을 생성한다. orchestration은 날짜·모델 버전·기준일·IC/NW t/표본수의 기존 기준과 각 통과 여부를 재검증한다. 단순히 프로세스가 실패했다거나 보고서에 `publishable:false`만 있다고 정상 보류로 간주하지 않는다. 품질 기준은 IC >= 0.01, NW t >= 2, 평가일 >= 60으로 유지한다. 발행 결과는 기존 원자적 RPC의 성공 반환 후에만 기록한다.

최종 영수증 `weekly-execution.json`은 `weekly-execution-<금요일>-<run_id>-<run_attempt>` artifact로 90일 보존한다. 품질 보고서에도 attempt를 붙여 rerun 시 artifact 이름이 충돌하지 않는다. 영수증 업로드까지 기존 concurrency 잠금을 유지하므로 다음 실행은 직전 결과를 읽은 뒤 판단한다. rerun도 같은 run의 이전 attempt들을 확인한다. 영수증은 잠금 자체가 아니므로 다른 workflow/group에서 모델을 직접 실행하는 경로를 추가하면 안 된다.

감시 워크플로도 동일한 분류기를 사용한다. 기존 비인증 공개 API 조회 대신 서버 인증 배치 조회와 Actions 영수증을 확인해 품질 보류를 파이프라인 누락으로 오인하지 않는다. 감시는 조회/기존 이슈 알림만 수행하고 학습은 시작하지 않는다. 토요일 00:12·17:12 KST에 확인한다. 감시 자체가 복구 창 밖으로 늦어져도 최근 마감한 금요일의 발행/보류 증거를 판정한다. 학습은 설치 직후에도 복구 마감 시각을 다시 검사한다.

## 안전 경계와 운영 확인

- `contents: read`, `actions: read`만으로 실행 증거를 읽는다. 주간 워크플로에 actions write/dispatch 권한을 추가하지 않는다. 감시의 기존 issues write 권한은 유지한다.
- service role은 서버 환경변수에서만 사용하며 익명키로 폴백하지 않는다. HTTP 오류 본문/서명 URL/자격증명 예외를 로그에 출력하지 않는다. artifact 다운로드의 storage redirect에는 GitHub Authorization 헤더를 전달하지 않는다.
- 운영 DB/추천/자동매매 데이터를 이번 작업에서 변경하지 않았다. 실제 모델 학습, workflow dispatch/rerun, 운영 API 거래 호출, 마이그레이션도 실행하지 않았다. 기존 `publish_recommendations` RPC와 거래 인증/품질 기준을 변경하지 않았다.
- 과거 학습 실행에는 새 영수증이 없다. 특히 10월 30일의 legacy exit 1을 자동 재학습 허가로 전환하지 않는다. 기존 기록이 불명확한 동일 주차는 안전하게 차단하며 새 주차부터 새 영수증이 누적된다. 이 PR은 현재 주차 추천을 강제로 발행하는 변경이 아니다.
- 증거 조회 실패 시 Actions의 정적 오류 사유를 먼저 확인한다. 누락된 인증/권한이나 artifact 오류를 고치고 같은 복구 창에서 재실행한다. 이미 학습했을 가능성이 있는 영수증을 삭제하거나 가짜 완료/보류 파일로 채워 재시도를 허용하지 않는다. 복구 창 밖의 과거 발행은 별도 검토가 필요하다.
- API 조회 실패 시에도 학습을 진행하던 기존 fail-open 동작은 제거했다. 이는 공급자 장애 시 발행보다 중복/불명확 실행 방지를 우선하는 의도된 변경이다.
- GitHub는 pending concurrency 실행을 교체하거나 schedule 자체를 모두 지연/드롭할 수 있다. 보완/감시도 GitHub schedule이므로 전달 시각을 보장하지 않는다. 정시 SLA가 필요하면 별도 외부 스케줄러를 연결하되 같은 기본 브랜치 워크플로/guard를 호출해야 한다. 이번 PR에는 외부 서비스나 추가 비밀키를 도입하지 않는다.
