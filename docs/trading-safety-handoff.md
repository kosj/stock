최신 DB 이력·배포 결과는 `migration-reconciliation-20261020.md`를 우선한다.
아래 미실행/중복 버전 표시는 최초 작업 당시 기록이며, 과거 SQL을 다시 실행하지 않는다.

작성: 2026-10-19 KST. 요청: 코드 리뷰에서 제안한 순서대로 수정하고 새 세션용 기록 남기기.

## Supabase CLI 설치 (2026-10-19 추가)

- 클라우드 작업 공간의 저장소 루트에 Supabase CLI **2.121.0**을 npm 개발 의존성으로 설치했다.
  `package.json`에 정확한 버전을 고정했으며 `npx --no-install supabase --version`으로 실행을 확인했다.
- 실행: 저장소 루트에서 `npx supabase <명령>`. 사용자 PC의 전역 설치는 아니다.
- 새 작업 공간에서는 `npm install`로 복원한다. npm 설치 스크립트를 차단하는 환경에서는
  CLI 실행파일 설치 여부를 별도로 확인해야 한다.
- 이번 설치에서는 로그인, 원격 프로젝트 연결, 로컬 DB 시작, DB 마이그레이션을 실행하지 않았다.
- 원격에 `db push`를 하기 전 기존 마이그레이션 이력과 파일의 버전/순서부터 확인해야 한다.
  기존 20261019 SQL 두 파일은 날짜 접두어가 같아 CLI 이력용 고유 버전 정리가 필요하다.

## 1. 거래 안전성

- DB 계정별 실행 임대 잠금 추가: `SupabaseExecutionControl`, TTL 120초.
  HTTP 함수 최대 60초보다 길게 설정. 서버 프로세스 내부 잠금으로 대체하지 않는다.
- 잠금 RPC 미설치/오류는 매매 중단. `finally`에서 소유자 토큰으로만 잠금 해제.
- 추천 오류·없음·불완전·만료: 신규 매수/순위이탈 청산 중단, 기존 보유 손절 검사는 계속.
- 추천 검증: 같은 기준일의 20개, 순위 1~20 연속/유일, 티커 중복 없음, 양수 유한 가격.
  KST 기준 이전 날짜이고 7일 이내여야 함. 당일 산출 추천으로 당일 체결하지 않는다.
- 완료 메타데이터 `recommendation_batches`가 존재하는 배치만 엔진에서 사용.
- 체결 이력 조회 오류는 구매 중단. 당일 모든 매도 이력으로 이전 실행의 손절 후 재매수 방지.
- 주문 키는 `auto:user:KST일자:방향:티커`. 수량 변경으로 중복 주문을 우회하지 않는다.
- 기존 비멱등 레거시 RPC 폴백 제거, 계좌·포지션 조회 실패를 가짜 기본값으로 숨기지 않는다.
- SQL 매수/매도 모두 계좌→포지션 순서 잠금, 잠금 후 중복 주문 검사.
  음수·0 수량과 유효하지 않은 가격 거부. RPC 직접 호출은 service_role만 허용.

## 2. 비용 / 체결 / 자본

- 추천 생성: 금요일 16:12 KST. 자동매매: 평일 09:12 KST 단일 예약.
  다음 거래일 최초 실행에서 새 추천 사용. GitHub 예약 지연 시 정규장 외 주문 거부.
- 장중 09:00 이상 15:30 미만만 즉시 체결. 주말은 차단.
- 실행 시세는 실제 거래소 거래 시각이 10분 이내인 경우만 사용(최대 미래 오차 1분).
  HTTP 조회 시각을 실제 거래 시각으로 간주하지 않는다.
- Yahoo `regularMarketTime`을 보존한다. Naver 폴백에서 실제 거래시각이 없으면
  해당 시세는 화면 표시용이며 매매는 건너뛴다. 이로 인해 운영 체결 건수가 줄 수 있다.
  공휴일 캘린더는 아직 없으나 휴일의 전일 시세를 최신가로 체결하는 것은 차단한다.
- `execution-policy.ts`의 공통 실효가격 계산을 자동매매·수동 모의거래·리플레이가 사용.
- 기본 **시뮬레이션 가정**: 수수료 0.015%, 불리한 슬리피지 0.1%, 세금 0.
  세금 0은 면세 판정이 아니라 미설정 기본값이다. 순수익 비교 전 반드시 종목별 세율 검증/설정.
- 서버 환경변수:
  - `MOCK_FEE_RATE`: 소수 비율 (예: 0.00015)
  - `MOCK_SLIPPAGE_RATE`: 소수 비율 (예: 0.001)
  - `MOCK_SELL_TAX_RATES`: 티커→소수 세율 JSON. 법정 세율은 여기서 추정하지 않는다.
- 운용 한도는 **보유 평가금액 + 신규 투입액** 상한. 매도 후 잔액 재조회하고
  `min(잔액, max(0, 한도 - 보유평가액))`만 사용. 기존 한도 초과 보유를 강제 청산하지는 않는다.
- 기존 수동 보유도 같은 계좌 평가액에 포함(보수적). 자동/수동 분리 계좌는 미구현.
- 시세 결손 보유가 있으면 불확실한 평가액으로 매수하지 않는다.

## 3. 동일 엔진 백테스트

- `frontend/lib/core/trading-engine.ts`가 운영과 리플레이의 단일 전략 구현.
- `frontend/lib/core/replay.ts`: 현금·평단·포지션·멱등 체결·비용을 가진 과거 브로커.
- 실행: Node >=22.18 (권장 24), `npm run backtest:trading -- snapshots.json > result.json`.
- 입력 형식 `ReplayInput`:

```json
{
  "initialCash": 10000000,
  "capital": 5000000,
  "costs": {"feeRate": 0.00015, "sellTaxRate": 0, "slippageRate": 0.001},
  "batches": [{
    "completedAt": "2026-10-16T17:00:00+09:00",
    "rows": [{"runDate":"2026-10-16","rank":1,"ticker":"005930","name":"삼성전자","recommendation":"buy","currentPrice":100000,"baseReturn30d":0}]
  }],
  "sessions": [{"at":"2026-10-19T09:12:00+09:00","prices":{"005930":100000},"benchmark":3000}]
}
```

위 예시의 rows는 형식만 보여준다. 실제 실행에는 같은 날짜의 유효한 순위 1~20이 필요하다.
`completedAt <= 세션 시각`인 추천만 노출한다. 과거 생성시각이 없는 추천은 임의로
당일 장전 생성된 것으로 가정하지 않는다. 가격은 반드시 해당 시각에 관측 가능했던 값만 제공.
일봉 종가를 오전 09:12 가격처럼 넣으면 미래참조가 되므로 금지한다.

출력: 비용 반영 계좌가치·수익률·최대낙폭·시장 대비 수익·회전율·체결·매매 이유.
벤치마크가 전 세션에 없으면 시장 대비 수익은 null. 결손 평가액은 stale 플래그 표시.
수익률은 설정되지 않은 세금을 포함하지 않는다. 리플레이는 자동 종목별 세율이 아니라
입력 costs의 공통 세율을 사용하므로 혼합 세율 자산 비교에는 추가 확장이 필요하다.
장중 손절 보장·호가잔량·체결 대기·생존편향은 미구현. 기본 손절은 실행 시점 검사일 뿐이다.
기존 `backtest_recommendations.py`는 추천 품질 진단용으로 유지하며 전략 수익률과 혼동하지 않는다.

## 4. 추천 모델 / 표시 / 저장

- 추천 발행을 단일 DB RPC 트랜잭션으로 변경. DELETE 성공 후 INSERT 실패 시에도
  기존 완료 배치가 보존된다. 부분 결과는 공개하지 않는다.
- 기준일은 KST. 종목의 최신 가격 일자를 벤치마크 기준일로 맞추고 결손 종목 제외.
- 벤치마크 선행수익은 일수익률 합이 아닌 실제 복리수익률로 계산.
- Ridge 메타모델도 날짜 단위 forward-only 검증 + TARGET_DAYS 간격으로 평가.
  기존 티커 블록 KFold와 단순 베이스 평균 대리지표 제거.
- 추천 품질 게이트: 일별 OOF IC >=0.01, Newey-West t >=2, 평가일 >=60.
  미달하면 실패 종료하여 기존 배치를 유지. 임계값은 운영 정책이지 수익 보장이 아니다.
- 기존 분위수 기반 수익률 숫자는 분석 호환을 위해 DB에 남기되
  `return_calibrated:false`로 표시. 추천 목록은 상대 매력도 점수·OOF IC를 보여준다.
- 개별 종목 화면에서도 미보정 배치의 퍼센트로 절대 주가 경로를 만들지 않고 안내를 표시.
- 실제 수익률 보정, 가중치/손절 최적화는 **실제 과거 데이터 검증 후** 해야 한다.
  이번 변경으로 수익성이 개선되었다고 주장할 근거는 아직 없다.

## 운영 적용 순서 (미실행)

1. 변경 사항을 검토하고 GitHub에 보존한다(기존 사용자 변경을 섞지 않는다).
2. Supabase 관리자 연결로 다음 파일을 순서대로 적용:
   - `supabase/migrations/202610190002_trading_safety.sql`
   - `supabase/migrations/202610190001_mock_order_guards.sql`
3. `SUPABASE_SERVICE_ROLE_KEY`와 비용 환경변수를 서버에 설정한다.
   service role 없는 서버에서는 강화된 RPC 실행 권한이 없어 의도적으로 실패한다.
4. 새 코드 배포. 기존 배치를 완료 배치로 임의 승격하지 않는다.
5. 승인된 추천 생성 작업을 실행하여 품질 게이트를 통과한 최초 완료 배치를 만든다.
   그전에는 신규 매수/순위이탈 청산을 중단하고 손절 검사만 수행한다.
6. 장중 시세의 실제 거래시각 제공 여부와 비용 설정을 확인한 뒤 모의투자 스모크 검증.
7. 실제 과거 입력 스냅샷을 마련해 기존/신규 전략 성과 비교. 아직 실측 결과 없음.
